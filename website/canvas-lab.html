1. Open and inspect the starter

  1. Extract the ZIP. Open the website folder in your editor or connected coding agent.
  2. Read README.md, AGENTS.md, and TASK.md. The instruction files guide an agent; they are not agents by themselves.
  3. Run the website with VS Code Live Server, or open a terminal in website and run py -m http.server 8000 on Windows (python3 -m http.server 8000 on macOS/Linux). Visit http://localhost:8000. Double-clicking the HTML is not the recommended preview.
  4. Save a before screenshot and identify one confusing task. If you want to add a university fact, find its official source.

2. Write the brief before asking for code

Complete TASK.md: audience, task, observed problem, one improvement, allowed files, and three observable tests. For example: “On a phone, open the menu, choose Campus map, and arrive at the map section.”

3. Work with your agent

Use one agent as your designer, builder, and tester in sequence. You do not need several agents. Start with this prompt:

Read README.md, AGENTS.md, and TASK.md. Ask me three short questions, one at a time, about my audience, their task, and the current problem. Suggest two small designs and explain the tradeoffs. Wait for my selection before changing code. After building, test my criteria and report what you actually observed.

Then use AGENT_PROMPTS.txt in the ZIP for the build, test, and reflection stages. A chat without folder/repository access can suggest code; you must apply the returned files yourself.

The loop: choose a goal → make a small change → run it → observe → fix → test again. Stop when your three criteria pass and you have a peer-test record, or after three build/test rounds. If you reach the limit, document what is unfinished.

4. Test with another student

  1. Give your partner a task without showing them where to click.
  2. Observe whether they finish, where they hesitate, and what they misunderstand.
  3. Check your feature on a narrow screen and using the keyboard.
  4. Fix one observed problem and retest. If you find none, explain one limitation and test an edge case.
  5. Append actual results to TEST_LOG.md. Run node test-core.js if Node is available; mark it unrun if it is not. Those existing data tests do not replace the browser checks for your new feature.

5. Keep the design useful and honest

  • Keep the educational-prototype label and media credits. Label proposed AI pages and buildings as proposals.
  • Verify university claims; do not invent hours, policies, available services, or accessible routes.
  • An AI learning page can be fully interactive without a live AI API. Label scripted responses as scripted.
  • Do not put private API keys or real student records into this public website.
  • Ask: Who might struggle with my design? Consider phone users, commuters, beginners, and people using a keyboard or assistive technology.

6. Publish and submit

Create your own GitHub repository and upload the contents of website/, so index.html is at its root. Preserve the asset folders and relative links. In repository Settings → Pages, choose Deploy from a branch → main → /(root) → Save. Test the actual published URL shown by GitHub. Public repositories can use GitHub Pages on GitHub Free.

GitHub's official publishing instructions

Browser-only edits do not update GitHub. If you added resources or videos through the site's forms, export the data and follow README.md to put it in config.js before publishing.

Submit these items in Canvas:

  • Published website URL and repository URL (or a code ZIP if your instructor approves that fallback).
  • Completed TASK.md, AI_USE.md, and your new TEST_LOG.md entries; these may live in the linked repository.
  • Before/after screenshots and a 60–90 second demonstration.
  • A short reflection: whom you helped, one AI suggestion you changed/rejected, what the peer test revealed, and one remaining limitation.
